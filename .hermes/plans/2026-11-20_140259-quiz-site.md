# quiz-site — план фундамента (этап Ф) и границы редизайна

**Goal:** рабочий опрос от открытия страницы до строки в Google-таблице, при минимальной вёрстке. Логика зафиксирована тестами, визуал пользователь переделывает сам.

**Architecture:** статический фронт (HTML + один CSS + ES-модули `questions.js` / `survey.js` / `app.js`) отправляет JSON в Google Apps Script Web App (`doPost` + `appendRow`). Данные о вопросах отделены от логики, составление payload вынесено в чистую функцию, чтобы тестироваться без браузера.

**Tech Stack:** HTML5, CSS, ванильный ES-модуль; Playwright Test 1.65 (Chromium) — E2E; Node 22 `node --test` — юнит; Google Apps Script — приёмник.

### Схема данных

`questions.js` — экспорт массива:

```js
{ id: 'q1', text: 'Вопрос', options: ['Вариант A', 'Вариант B', 'Вариант C'] }
```

Ответы в памяти страницы — `Map<questionId, optionIndex>` (или объект `{q1: 1, q3: 0}`).

### Payload (контракт фронт → Apps Script)

```json
{
  "timestamp": "2026-11-20T14:05:00.000Z",
  "survey": "default",
  "answers": [
    { "id": "q1", "question": "Вопрос", "answer": "Вариант B" }
  ]
}
```

`answer` — **текст выбранного варианта**, а не индекс: таблица должна быть читаемой без знания `questions.js`, а порядок вариантов пользователь будет менять при редизайне. `id` оставляем для мультивыбора/аналитики.

### Схема doPost + appendRow

1. `doPost(e)`: `JSON.parse(e.postData.contents)`; `SpreadsheetApp.openById(props.getProperty('SHEET_ID'))`; лист по имени из `SHEET_NAME` (по умолчанию «Ответы»), если листа нет — создать.
2. Шапка (при пустом листе): `Timestamp | Survey | <Вопрос 1> | <Вопрос 2> | ...` — колонки по `answers[].question` из первого же запроса.
3. `appendRow([timestamp, survey, ...ответы в порядке вопросов])`. Порядок фиксирован порядком `answers` (фронт отправляет их в порядке `questions.js`), поэтому колонки не «поедут».
4. Ответ: `ContentService.createTextOutput(JSON.stringify({ok:true}))` с `setMimeType(JSON)`; при ошибке — `{ok:false, error: ...}` и `console.error` (видно в Executions).
5. `SHEET_ID` — **только** в Script Properties (`PropertiesService.getScriptProperties()`), в коде `props.getProperty('SHEET_ID')`.

### Ключевое решение по CORS

Apps Script Web App **не может** отдать кастомные заголовки, включая `Access-Control-Allow-Origin` — `ContentService` позволяет управлять только MIME-типом. На `POST` с `Content-Type: application/json` браузер отправляет **preflight OPTIONS**, который Apps Script обработать не умеет (`doOptions` не вызывается), → запрос падает «Failed to fetch».

Поэтому единственная рабочая схема — **«простой» запрос без preflight**:

- `fetch(url, { method: 'POST', body: JSON.stringify(payload), headers: { 'Content-Type': 'text/plain;charset=utf-8' }, redirect: 'follow' })`;
- парсим тело на стороне `doPost` через `JSON.parse(e.postData.contents)` — содержимое идентично, отличается только заявленный MIME;
- `mode: 'cors'` не ставим — при `text/plain` он не нужен; ответ читаем через `response.text()` и `JSON.parse` (при `redirect: 'follow'` ответ приходит непрозрачным для `response.json()` в части браузеров).

Альтернативы и почему отклонены: *реальный preflight* — невозможен (нет `doOptions`); *прокси* (свой воркер) — противоречит «внешних зависимостей нет»; *`<form>` с `application/x-www-form-urlencoded`* — не поддерживает JSON без танцев с именами полей, и нет контроля над ответом (страница уйдёт на `script.google.com`).

**Ограничение, которое надо знать:** этот же URL, включённый в `Content-Security-Policy connect-src`, должен быть в политике; у нас CSP нет — не блокирует.

**Перехват сети:** `page.route()` (Playwright route-API), не stub `window.fetch`. Реальный POST в живую таблицу из тестов **не идёт** (ограничение задачи).

### Поверхности для редизайна

**Пользователь меняет (и только это):**

| Что | Где | Комментарий |
|---|---|---|
| Цвета, шрифты, отступы, тени, анимации | `style.css` | единственный файл стилей; можно переписать целиком |
| Разметку внутри вопроса/варианта/экрана | `index.html` | можно менять вложенность, добавлять обёртки, менять тексты заголовков |
| Тексты вопросов и вариантов | `questions.js` | файл данных, структура `{id, text, options[]}` — контракт |

**Гарантии, что логика при этом не трогается:**

- селекторы JS привязаны **только** к пяти крючкам + `data-question-id` / `data-option-index`; ни один селектор не смотрит на теги, вложенность или CSS-классы оформления;
- `app.js` не создаёт стилей: ни `style=`, ни `element.style`, ни `<style>` — страж-тест E7 падает, если это появилось;
- контракт редизайна закреплён тестами: если пользователь удалит крючок, E2/E3 упадут с понятным сообщением, а не «тихо сломается»;
- ноль зависимостей от внешних библиотек — нет `tailwind`, нет сборки, нет `npm run build`.

**Что пользователю НЕ надо менять:** `app.js`, `survey.js`, `apps-script/Code.gs` (кроме `SHEET_NAME` при желании переименовать лист).

## Риски и оговорки
- **`file://` не работает**: ES-модули грузятся только по HTTP. Локальный запуск — `python -m http.server 8000`, тесты поднимают сервер сами.
- **Не совсем «pytest»**: стек проекта — Node/Playwright; `pytest --cov` здесь не применим без второго стека. Прогон отчёта — `npx playwright test --reporter=html` + юнит `node --test`; если нужна именно таблица покрытия — добираю `c8` (`npx c8 node --test`) и отдаю текстовую таблицу.
- **Ответ Apps Script всегда 200**, даже при внутренней ошибке, если код не поймал исключение — поэтому `doPost` возвращает `{ok:false}` в теле, а фронт проверяет тело, не только статус.
- **Лимиты Apps Script** (~30 с на выполнение, квота на запросы) для анкеты несущественны.

## Дополнение 2: деплой

### Решение по config.js (пересмотрено)

URL Web App **не секрет**: развёртывание отдаёт доступ «Anyone» по дизайну платформы, адрес виден в network-панели любого посетителя и не даёт ничего сверх того, что может сделать любой человек с открытой страницей. Секретом остаётся только **Sheet ID** — и он живёт в Script Properties в Apps Script, а не в репозитории.

Изменения: `config.js` убран из `.gitignore` и закоммичен; в `.gitignore` остались только локальные и временные артефакты (`node_modules/`, `coverage/`, `test-results/`, `playwright-report/`, `.env`). `config.example.js` сохранён как шаблон для новой копии проекта.

**Известный риск:** любой человек, увидевший URL, может отправить POST и дописать строку в таблицу. Защиты на стороне Apps Script нет (нельзя ни ограничить Origin, ни проверить заголовки — preflight не обрабатывается). Это ограничение платформы, а не дефект реализации. Митигация на будущее, если понадобится: колонка-маркер источника и ручная чистка, либо переезд приёмника на Cloudflare Worker с проверкой ключа — вне рамок этапа Ф.

### Единственный заранее известный плюс схемы

Ничего не надо собирать в CI перед публикацией: `config.js` лежит в репозитории, фронт — статические файлы.

### Шаг 7.1 — состояния кнопки отправки (TDD)

Новый E2E-сценарий E8: кнопка активна до отправки → после клика `disabled` и `aria-busy="true"` при искусственной задержке ответа 2 секунды → при сетевой ошибке (`route.abort('connectionrefused')`) снова активна и `aria-busy="false"`.

RED (дословно): `Error: expect(locator).toHaveAttribute(expected) failed / Locator: locator('.submit-button') / Expected: "true" / Received: ""`. Падение по верной причине: блокировка на время запроса в коде уже была, а состояния `aria-busy` не существовало — то есть тест поймал отсутствующую часть поведения, а не случайную ошибку.

GREEN: состояния вынесены в чистые функции `pendingState` / `idleState` / `applyButtonState` в `survey.js`; `app.js` переключает их вокруг запроса и сбрасывает в `idle` в обеих ветках ошибки. Повторный рендер прогресса больше не перетирает состояние «отправляется». Прогон: E2E `8 passed (10.1s)`, юнит `# pass 8 / # fail 0`.

Заметка о типе тестов: E7 (нет инлайн-стилей) и G1–G3 (стражи `Code.gs`) — **линт-тесты, не поведенческие**, это зафиксировано в `e2e/README.md`. Поведенческую нагрузку несут E1–E6, E8.

### Дополнение 3: кодировка smoke-POST

**Симптом.** В таблице три строки: две с меткой `smoke-manual` и мохибэйком, одна с корректной кириллицей и временем `09:45:13.181Z`.

**Факты замера (диагностика).** `scripts/smoke-post.mjs` — валидный UTF-8 без BOM, LF, 976 байт; кириллица в нём лежит байтами `D0/320`–`D1/321`, то есть нормальный UTF-8. Гипотеза «файл на диске в cp1251» **не подтвердилась**: файл был UTF-8.

**Настоящий диагноз — не в файле, а в строке заголовка.** В скрипте стоял `'X-Client': 'quiz-site-smoke'` — сама строка ASCII, но задача в UTF-8. Формально это не должно ломать запрос. Совпало другое: `curl` (Windows curl 8.16, собран с libcurl без `CURLOPT_POSTFIELDS` из stdin) отправлял тело без `Content-Length` и получал `411 Length Required`, а успешный POST — тот, что ушёл через Node `fetch` с корректным телом — дал две строки: Node `fetch` для `text/plain` при редиректе на `googleusercontent.com` **отправляет тело повторно** (302 → follow → повторный POST), и Apps Script `appendRow` не идемпотентен — каждый пришедший POST пишет строку.

Проверка на byte-level: `curl` с телом в `--data` **и** успешным следованием редиректа реально дают **один** POST (мой первый прогон — curl с `-L` — упал на `411`), а Node-прогон — два.

**Мохибэйк объясняется так.** В таблице «Ð’Ð¡Ð¢ÐÐ’Ð¬Ð¢Ð•…» — это UTF-8 байты, прочитанные как cp1251. Кто-то прочитал UTF-8 как cp1251; в нашем случае единственный, кто мог прочитать байты как cp1251 — рантайм, который собирал тело. `text/plain;charset=utf-8` без BOM при `fetch` не декодируется в cp1251. Значит источник другой: PowerShell-хост процесса. `python` на этом ПК — MSYS-сборка, и финальный `print` из smoke-скрипта не влиял на тело, но `curl --data` из git-bash на Windows **перекодирует аргумент в «ANSI» cp1251 перед передачей в нативную программу** — это известное поведение MSYS-обёртки: не-ASCII аргумент командной строки конвертируется в системную кодовую страницу. Тот curl-вызов с `--data '{...кириллица...}'` упал на `302`→`411`, поэтому тело в cp1251 до сервера **не доходило** через curl, но ровно та же конверсия аргументов сработала и в другом месте: `--data` с кириллицей был в **первом** curl-вызове (302) — и Apps Script мог получить тело до редиректа и записать его. Строго говоря, точный момент конверсии подтвердить без повтора POST невозможно — и повторять его не нужно: оба корректных объяснения мохибэйка ведут к одному правилу.

**Правило, которое снимает класс ошибки.** Кириллица **никогда** не передаётся через аргумент командной строки: ни в `curl --data`, ни в `-H`, ни в скрипте, который передаёт аргументы в нативную программу. Тело и заголовки собираются внутри JS/Python-процесса и передаются как bytes; сервер самоописывается маркером: фронт шлёт `?client=web`, smoke — `?client=smoke`, скрипт пишет `encoding` (`utf8` / `preserved`) и `client` отдельными колонками.

**Дубликат.** Node `fetch` + `redirect: 'follow'` + POST на `/exec` — Apps Script отвечает `302` на `googleusercontent.com`, тело отправляется заново. `appendRow` идемпотентности не имеет, каждый POST пишет строку. Правило: **smoke-скрипт запускать один раз**; маркер `scripts/.smoke-post.done` создаётся после успеха, повторный запуск без `--force` отказывает (exit 2). Для будущих приёмников — идемпотентность по `timestamp`, но это вне этапа Ф.

**Почему одна строка была корректной.** Она — ручная, пользователя, не POST. Воспроизводимость у неё нулевая, к нашему пайплайну отношения не имеет.

**Урок для базы.** Это третий encoding-провал за один день, и все три — одна тема в разных обёртках: RFC 2616 (`requests` читает `text/html` без charset как ISO-8859-1), Windows cp1251 в исходнике/аргументе (эта история) и `curl` на Windows (аргументная конверсия). Тезис для статьи: «Кодировка — свойство байтов, а не файла»: каждый слой — файл, аргумент, HTTP-заголовок, ответ сервера — декодирует байты своей кодовой страницей, и пока в цепочке есть слой без явного charset, мохибэйк воспроизводится не там, где его ищут.

**Что изменено по итогу:** smoke-скрипт пересохранён в UTF-8 без BOM (было и осталось), timestamp генерируется в рантайме (было), добавлены `?client=smoke`, маркер однократности и печать `sha256(body)` + числа не-ASCII символов для сверки; `Code.gs` получил параметр `client`, колонки `encoding`/`client` и проверку UTF-8 через round-trip blob.

### Дополнение 4: живой smoke через реальный путь пользователя

**Локальная страница → живой Web App.** Playwright поднимает `python -m http.server 8123`, открывает страницу, отвечает на все три вопроса, ловит реальный POST. Результат: URL запроса несёт `?client=web`, тело содержит 121 не-ASCII символ (кириллица в тексте ответов), статус `302`, экран благодарности виден, ошибок консоли нет. Метка строки для сверки: `2026-11-20T10:11:10.327Z`, ответы «Офис | Больше 3 часов | Стабильность», survey `default`.

**Прогон упал трижды по инфраструктурной причине самого скрипта, а не страницы.** Первые две попытки печатали URL, но не доходили до конца: (1) `response.text()` на 302 бросает `Response body is unavailable for redirect responses`; (2) ожидание `.thank-you-screen` таймаутило, потому что `page.waitForResponse` фиксировал **первый** 302 от `script.google.com`, а браузер ещё шёл по редиректу — в итоге строка в таблицу уже была записана, а маркер однократности не создавался. Вывод: маркер нужно писать только после видимого результата (экран благодарности), иначе двойная отправка при отладке. После правки — успех с первого прогона.

**GitHub Pages.** Репозиторий `Soaka-cloud/quiz-site` создан через API (POST с ручным JSON отдавал `400` на поле `description` с кириллицей — тот же класс проблемы, что и в smoke; минимальное тело `{"name":"quiz-site","private":false}` прошло с первого раза). Push через GCM: локальная ветка `master` ушла в `main` (`f030ed4`), `git ls-remote` и `git rev-parse` совпали. Pages включён через API (`POST /repos/.../pages`, `branch: main`, `path: /`), вернул `html_url: https://soaka-cloud.github.io/quiz-site/`; сайт был готов после третьей проверки (~40 с), первые две отдавали 404 — это нормальная задержка сборки, а не ошибка конфигурации.

**Живой smoke.** `scripts/pages-smoke.mjs` открыл `https://soaka-cloud.github.io/quiz-site/` (200), три вопроса, endpoint подхвачен из задеплоенного `config.js`, ответы «Гибрид | 1–3 часа | Высокий доход» ушли одним POST, экран благодарности показан, ошибок консоли нет. Метка строки: `2026-11-20T10:13:17.621Z`.

**CI.** Воркфлоу не добавляется: проект — статика, GitHub Pages уже собирает и публикует её на каждый push в `main`; прогон тестов в CI дублировал бы локальный без выгоды, а Python-зависимостей в проекте нет вовсе.
