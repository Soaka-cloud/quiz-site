# Encoding: четыре лица одной темы

**Короткая версия.** Кодировка — это не свойство файла и не свойство «сайта». Это свойство байтов в конкретном слое цепочки: на диске, в аргументе процесса, в заголовке запроса, в теле по проводу, в ответе сервера. Пока хотя бы в одном слое нет явного charset, мохибэйк образуется там, где его не ищут, а статус ответа при этом выглядит нормальным. За один рабочий день одна и та же тема пришла четыре раза — в четырёх разных обёртках. Ниже — цепочка слоёв, четыре кейса и чек-лист, который из них вытекает.

---

## Слои цепочки и их дефолты

| Слой | Дефолт, когда charset не задан | Типичный провал |
|---|---|---|
| Файл на диске | нет дефолта: байты как есть | файл в cp1251, а читают как UTF-8 (и наоборот) |
| Аргумент / окружение процесса | системная ANSI-страница Windows (для MSYS-обёрток) | кириллица в `--data`/`-H` перекодируется до нативной программы |
| Заголовок запроса | `fetch`/браузер: UTF-8; ручной `curl`: байты без обещаний | сервер не знает, как читать тело |
| Тело в сети | как решено выше | расхождение «что обещали / что послали» |
| Декодирование на сервере | по заголовку, иначе эвристика платформы | тихая замена символов на `�` |
| Чтение ответа клиентом | **RFC 2616**: `text/*` без charset → `ISO-8859-1` | кириллица из ответа приходит мохибэйком |

Практический смысл таблицы один: **на каждой границе нужен явный charset**. Не «где-то настроили», а на каждом переходе.

---

## Кейс 1. Чтение: RFC 2616 и `requests`

Статический сервер отдал страницу с `Content-Type: text/html` — без `charset`. Клиент на Python (`requests`) применил дефолт стандарта: `ISO-8859-1` для `text/*`. Кириллица в теле — в UTF-8; после декодирования как latin-1 получаем `Ð\x9bÐµÐ½Ð´…`.

Ловушка в проверке: `if response.encoding is None` **не срабатывает** — значение не пустое, оно `ISO-8859-1`. Проверять надо по значению:

```python
if not response.encoding or response.encoding.lower() in ("iso-8859-1", "ascii"):
    response.encoding = response.apparent_encoding or "utf-8"
```

Правило: читаешь текст из сети — спроси себя «а какой charset мне пообещали», и если ответа нет, назначь его сам, а не наследуй дефолт стандарта.

## Кейс 2. Передача: MSYS-аргументы на Windows

Скрипт собирает JSON с кириллицей и передаёт его в `curl` аргументом:

```
curl --data '{"answer":"Удалённо"}' https://endpoint/exec
```

Из git-bash (MSYS) нативный `curl.exe` получает **не** эти байты: MSYS перекодирует не-ASCII аргументы в системную ANSI-страницу (на русской Windows — cp1251). В теле оказывается «Удалённо» в cp1251, сервер читает его как UTF-8, в таблице появляется мохибэйк. Файл при этом был честный UTF-8 — потому диагноз «пересохраните файл в UTF-8» и оказался ложным следом.

Что помогает:

- тело передавать **stdin** или файлом, не аргументом: `curl --data-binary @body.json`;
- заголовки — только ASCII (не-ASCII значение заголовка убивает `fetch` ещё до отправки: `Cannot convert argument to a ByteString`);
- контроль на месте: `printf '%s' 'привет' | xxd | head -1` покажет, что реально уходит.

## Кейс 3. Редирект: 302 съедает тело и код

`curl` на endpoint, который отвечает `302`, печатает `HTTP=302` — выглядит как успех. По факту: тело ушло, ответ остался непройденным. С `-L` всплывает `411 Length Required` — при ручном следовании редиректу теряется `Content-Length`.

Тот же редирект ломает и браузер, если хост из `Location` недоступен: `fetch` не получает ни ответа, ни ошибки и висит, пока не истечёт таймаут. Клиент должен иметь свой таймаут (`AbortController`), а чтение тела ответа — `try/catch`: в браузере `response.text()` на 302 бросает `Response body is unavailable for redirect responses`.

Правило: **редирект-хост — часть контракта приёмника.** Если платформа редиректит на другой хост, клиент зависит и от него тоже.

## Кейс 4. Валидация API: 400 на кириллическом описании

`POST /user/repos` с телом, где `description` содержит кириллицу, вернул `400`. Тело без не-ASCII (`{"name": "...", "private": false}`) прошло с первого раза. Ни статус, ни сообщение не указывали на кодировку — только сравнение двух запросов, отличавшихся ровно одной строкой.

Правило: когда 4xx непонятен, строй **контрольную группу** — минимальное тело из ASCII. Расхождение между «полным» и «минимальным» запросом локализует проблему быстрее, чем чтение документации.

## Бонус-кейс: файл на сервере ≠ файл в браузере

Это не про кодировку, но из той же семьи «где именно мы смотрим». Проверка через `curl` и `sha256` доказала: на сервере лежит новый код. В таблице при этом были результаты старого. Причина — браузер исполнил кэшированную копию статики (`Cache-Control: max-age=600`). Проверка сервера ничего не говорит о том, **что исполнил клиент**. Проверять поведение — только в чистом браузере (или после hard reload).

---

## Мета-тезис: код возврата ≠ результат

У всех пяти историй общий корень. Инструмент сообщает что-то **о себе** — статус 302, `ok:true`, «файл записан», «200 OK» — и это принимают за результат. Настоящий результат проверяется отдельно:

- строка появилась в таблице (а не «скрипт сказал 200»);
- в браузере исполнился новый код (а не «на сервере новый файл»);
- байты дошли в той кодировке, которую обещали (а не «файл был UTF-8»).

Практика, которая это чинит: **уникальный маркер на каждый вызов** (например, timestamp в payload), сверка по маркеру, и запись маркера «уже выполнено» **только после** подтверждённого эффекта. Иначе отладка сама генерирует дубликаты: в этом проекте так ушло четыре живых POST при договорённости об одном — каждый упавший после записи прогон оставлял строку.

## Чек-лист читателю

1. **Явный charset в обе стороны**: ставь в ответах сервера, передавай в запросах; не наследуй дефолты стандарта.
2. **ASCII на границах**: заголовки — только ASCII; параметры-метки (`?client=web`) — только ASCII.
3. **Тело — файлом или stdin**, не аргументом командной строки.
4. **Уникальный маркер на вызов** в самих данных, чтобы найти свою запись после падения.
5. **Проверяй эффект, а не ответ**: маркер в таблице, файле, БД — а не статус.
6. **Скрипт, который можно безопасно перезапустить**: маркер однократности + явный `--force`.
7. **Клиент не зависит от хостов вне контракта**: проверь, куда редиректит endpoint.
8. **Поведение проверяй в чистом браузере**: серверная проверка файла доказывает только наличие файла.

## Что было в этом проекте (источник фактов)

Все кейсы — из одной задачи: статический опрос на GitHub Pages, отправляющий ответы в Google Apps Script Web App, который пишет строки в Google-таблицу.

- RFC 2616: `http.server` + `requests` и мохибэйк в кириллице.
- MSYS: кириллица в `--data` из git-bash, cp1251 в теле, мохибэйк в таблице.
- 302/411: `curl` на Apps Script, «успех» по коду без результата.
- 400: GitHub API, описание репозитория на кириллице.
- Кэш: новый `value` в файле, старый `label` в таблице.
